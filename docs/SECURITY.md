# Security

**Status:** current as of release 0.5.0, 2026-09-18.

This document states what OpenClerq protects today, what it does **not** protect today, and
the rules that bind future work. It supersedes the previous `SAFETY_CHECKLIST.md`.

---

## 1. Threat model

OpenClerq takes natural language, hands it to a language model, and acts on the result. As
the roadmap adds shell execution, git push and server installs, it becomes **a program that
executes model-generated instructions with local operating system authority**, and is
designed on that basis.

### Assets

| Asset                             | Why an attacker wants it                                   |
| --------------------------------- | ---------------------------------------------------------- |
| Provider API keys                 | Direct financial cost; access to the user's model accounts |
| Git credentials / GitHub tokens   | Write access to source repositories                        |
| Source code and repo contents     | Exfiltration target                                        |
| The gateway's execution authority | Arbitrary code execution on the host                       |
| The secrets vault                 | Everything above, at once                                  |

### Adversaries

1. **A malicious or compromised dependency** in a repo OpenClerq operates on.
2. **Prompt injection via repo content** — a README, issue body, changelog or dependency description crafted to redirect the agent. Repo content is untrusted input, and the agent reads it by design.
3. **Prompt injection via pasted content** — the same threat through the chat console. Pasted text is untrusted, and the console can draft scheduled jobs, so a model-drafted automation always saves disabled and pushes manually on its first run.
4. **A network-local attacker** reaching an exposed gateway port.
5. **A malicious skill, module or plugin** installed by the user.
6. **A confused model** — not adversarial, simply wrong, and destructive at scale because it is on a schedule.

### Explicitly out of scope

- A local attacker who already has the user's OS account. Anyone who can read `~/.clerq` as that user can read what the gateway can.
- Malicious model providers.
- Physical access.

## 2. What is protected today

- **The gateway is authenticated.** Every endpoint except `/health` and `/version` requires a bearer token, compared in constant time. There is no development bypass. The token is generated on first run at `~/.clerq/gateway-token` (mode 0600), or supplied via `CLERQ_GATEWAY_TOKEN`.
- **Scoped tokens.** A module UI's token reaches only its module's routes and the core endpoints its manifest declares, and expires (15 minutes by default). Scoped tokens are stored as SHA-256 hashes, can be revoked at once, and never reach token, device, remote or vault endpoints, the unfiltered `/events` or the logs. A scoped token of a tenant other than `default` reaches only what is kept per tenant.
- **Module permissions are declared, not enforced.** A manifest's `permissions` are parsed, listed and audited when they change, but module server code still runs with the gateway's full access.
- **Tenants are kept apart in the gateway.** Records, links, activities, inbox items and module tables are filtered by tenant, and a scoped token is bound to its tenant. Module code shares the process and the database, so a module's raw SQL must filter on its tenant itself; database-level isolation (row-level security) is planned.
- **Remote mode is opt-in, and the gateway stays on loopback.** `PUT /remote { enabled, publicUrl }` records the HTTPS address of the user's own tunnel or reverse proxy, which terminates TLS. Plain HTTP is refused except to localhost.
- **Phones pair with a single-use code.** `POST /devices/pairing` makes a code valid five minutes; `POST /devices/pair` (no token) trades it once for a device token. Only a hash of each is kept, and a code is 50 random bits. Past 30 wrong codes a minute the gateway answers `429` to wrong codes, while a right one still pairs. The gateway token never reaches the phone.
- **Device tokens reach only the mobile API set**: status, runs, approvals, pause and resume, the inbox, search and records (read). They expire after 30 days unused, stop working while remote mode is off, and `DELETE /devices/:id` revokes one at once. `GET /devices` shows each device's last-seen time.
- **Pushes carry no content.** Each paired device gets a random ntfy topic (ntfy.sh by default, or `PUT /remote { ntfyServer }`). A message is a generic title ("Approval needed", "New task") and an id such as `inbox:inb_…`; the phone fetches the details over the authenticated API. A vault secret `NTFY_TOKEN` is sent to servers that need one.
- **Module UI files are public.** `GET /api/modules/<id>/ui/*` needs no token: it serves only the module's static `dist/ui` files, and no other route can sit under it. They reveal which modules are installed, and nothing else.
- **The gateway binds loopback.** `127.0.0.1` unless `CLERQ_HOST` is set deliberately, which also logs a warning. The headless server logs the same warning, and [SERVER.md](SERVER.md) sets out what to do when it must be reached over a network.
- **CORS is allow-listed.** Origins are reflected only when explicitly configured. There is no wildcard path in any mode.
- **Filesystem reads are canonically contained.** `fs.read` resolves against a `realpath`'d root and rejects traversal, prefix-sibling escapes, absolute paths, NUL bytes, and symlinks leaving the root. Reads are size-capped and refuse non-regular files.
- **Outbound HTTP is SSRF-hardened.** `http.request` is unregistered without an allowlist. When enabled it permits https only by default, refuses URL credentials, resolves DNS and rejects loopback, private, CGNAT, link-local and cloud-metadata addresses, revalidates every redirect hop, and bounds both time and response size.
- **Local state is private to its owner.** `~/.clerq` is 0700 and every file holding keys, conversations or secrets is 0600, repaired at startup on installs made before this was enforced. Transcripts and prompts are stored unencrypted inside it: the protection is the account boundary, not encryption at rest.
- **Request bodies are bounded.** JSON parsing is capped (default 1 MiB).
- **No write tools ship.** There is no `fs.write` and no `exec` tool. The current blast radius is bounded by that absence, not by a policy engine.
- **Secrets are encrypted at rest.** AES-256-GCM with per-entry IV and auth tag. Values are never returned by the listing endpoint; `GET /secrets` returns names only.
- **Vault access is audited.** Set and delete operations append to `~/.clerq/secrets.audit.log`.
- **API keys are not bundled or logged.** The desktop app does not ship keys and does not send them anywhere except the local gateway.
- **The gateway's log lines reach the desktop app's stderr.** The app writes what its background service prints to its own stderr, one `[gateway]` line each, as the gateway wrote it: nothing is redacted on the way, and the lines include paths, ids and error text. Where that stderr ends up (a terminal, the system log, nowhere) depends on how the app was started. The lines pass through a queue of 256 and a thread of their own; when nothing reads stderr, further lines are dropped rather than waited for.
- **Numeric results are deterministic.** Calculations run in the Rust engine and return a `proof` object. The model never produces final numbers.
- **A chat's model cannot arm an automation through its tools.** It can only draft a spec. A person dry-runs and saves it; it is saved switched off with `authored_by: chat <session>`, marked "Written by a chat" beside its switch, and switching it on is a separate action. No chat tool saves, enables, edits or runs an automation, and every chat's policy denies those actions. A raw chat has no tools at all, and a managed one has no file or shell tools unless a folder is attached. This holds for the tools only: with a folder attached under Full access the agent's commands run as you, and can do what you can, including drive the gateway (see §3).
- **Automations cannot arm or publish themselves through OpenClerq.** A new automation is saved disabled. Pushing waits for a human unless the spec opts out, and an automation's first push always waits. The agent's environment does not contain the gateway token or provider keys, and the forge token reaches git through an environment-supplied header, never the command line or the remote URL. Under the default `native` profile that is all it is: the agent runs as you and can read `~/.clerq/gateway-token` from disk like any of your files (§3). The seatbelt and container profiles make `~/.clerq` unreadable.
- **Runs are durable and accountable.** Every task and trigger firing writes a run record with its request, its steps, and the tokens and cost of each model call. A model with no known price records an unknown cost rather than zero.
- **Approvals fail closed.** An approval nobody answers within the timeout is refused, never granted.
- **The kill switch stops everything in flight.** `POST /kill` refuses pending approvals, cancels running runs mid-call, and pauses triggers until `POST /resume`. `POST /runs/:id/cancel` stops a single run.
- **Responses are bounded.** A model response is capped (8 MiB by default, `CLERQ_MAX_RESPONSE_BYTES`): a streamed answer is cut off and marked truncated, a buffered one is refused.
- **The vault master key lives in the OS keychain** — macOS Keychain, libsecret on Linux, DPAPI on Windows — generated on first use. `CLERQ_VAULT_KEY` still works, with a warning; a host with no keychain uses `~/.clerq/vault.key` (mode 0600).
- **Sandboxed processes have no network by default,** and an egress allowlist is enforced at the process boundary rather than in the agent's HTTP tool. See the limits below.
- **Automations can run in a sandbox profile, if their spec asks.** `native` is the default (see the gap below); `seatbelt` and `container` are opt-in per spec. What each enforces, and what it does not, is set out in [§2.1](#21-automation-sandbox-profiles).
- **A GitHub App's tokens are short-lived, per repository and per purpose.** With a GitHub App connected ([GITHUB.md](GITHUB.md)), a run is given installation tokens instead of a personal access token: each lasts at most an hour, covers one repository, and has only the permissions of its purpose (fetch: read contents; push: write contents; pull request: write pull requests, read contents). They are kept in memory only, revoked when the run ends (finished, failed or cancelled; one that cannot be revoked expires by itself), never given to the agent or a gate, and redacted from everything the run stores. A token wider than asked for is revoked and refused. The pull request is opened by the app's bot, not by you. `/github` routes need the gateway token and no scoped token reaches them; the one without a token, GitHub's callback after the manifest, needs a single-use random state valid ten minutes and tied to the address it was made for.
- **Your GitHub sign-in is for identity and a list, never for acting.** Signing in to GitHub through the app's device flow ([GITHUB.md](GITHUB.md#sign-in-as-yourself-the-device-flow)) gives the gateway a user token that says who you are and lists the repositories you reach. It is kept in one reserved vault entry that no spec, agent, `/secrets` call or credential lookup can name, is in no answer or log line, is cut out of anything GitHub says, and is never used to clone, push or open a pull request: runs use the app's installation tokens. It is renewed with the app's client secret, or ends at expiry without one, and signing out revokes it on GitHub when the secret is stored.
- **Forge tokens reach git only as a header.** A remote repository is cloned and fetched, and a branch pushed, with the token in the environment of that one git command as an HTTP header scoped to the forge's host (`http.https://github.com/.extraheader`). It is never in the argv, the remote URL, the clone's config or the agent's environment. The diff and gate output stored with a run, the commit message and the pull request's title and body are redacted of the vault values the run uses. Redaction matches each value literally, values of 6 characters or more: a value encoded (base64, hex, URL-encoded) or split across lines is not found. The diff is also scanned with every file as text (a file marked `-diff` or holding a NUL byte included); when it contains a value, the push waits for approval. A secret the agent wrote into a file is still in the commit.

### 2.1 Automation sandbox profiles

`sandbox.profile` in an automation spec. The same profile applies to the agent process (a CLI), to every command the builtin agent runs, to the builtin agent's file tools (each read, list, write and edit is a small command run inside the profile, so the kernel bounds every path, links and concurrent renames included), and to the gates. The builtin agent's model calls run in the gateway. Under a profile an agent CLI needs `agent.api_key_secret`: it runs on a state home of the run's own and never on your sign-in or your `~/.claude`, `~/.codex` or `~/.cursor`. The gateway's own git commands (commit, diff, push) and the pull request run outside the profile, after the agent and the gates, and only once nothing they started is still running (below).

**`native` (the default).** No isolation. The agent and the gates run as your user, with your files and your network. The builtin agent's file tools run in the gateway behind a path check that a concurrently running command can race (by swapping a directory on the path for a link); nothing is promised there. Codex keeps its own `workspace-write` sandbox and Cursor its command allowlist, as described in [ARCHITECTURE.md](ARCHITECTURE.md#agent-drivers). A spec without a `sandbox` block runs this way, and the run records that it was unisolated. `sandbox.network` and `sandbox.filesystem` are refused for it: it cannot enforce them.

**`seatbelt` (macOS, `sandbox-exec`).** Apple has deprecated the tool; it still works on current macOS.

Each command (the agent, each of the builtin agent's commands and file operations, each gate) runs in a container of its own, named `clerq-<run>-<random>`, which is removed before the gateway goes on.

| **Updater key has no rotation path**             | Installed apps trust only the public key they shipped with. Losing the private key or its password ends in-app updates for every install; rotating it needs a release signed with the old key that carries the new one.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                  |

Release 0.4 closed the four blocking gaps (unauthenticated gateway, all-interface bind,
prefix-based path containment, licensing standing in for authentication) plus the SSRF and
CORS findings. The gateway is still intended for loopback use: remote exposure is a 1.0
feature and needs TLS and a reverse proxy in front of it.

**Treat the gateway token as a credential.** Anyone holding it can run tools on your machine.

## 4. Binding rules

A change that violates one of these does not merge.

1. **Localhost by default.** Network binding requires an explicit flag _and_ configured authentication. Never both defaults.
2. **No unauthenticated path, ever** — including in development. Generate a token on first run and hand it to the desktop app. `/health` and `/version` are the public endpoints, and they reveal no configuration.
3. **Authentication and licensing are separate concepts.** Licensing answers _is this install entitled to feature X_. Authentication answers _is this caller allowed to control this gateway_. Neither may substitute for the other.
4. **Sandbox by default wherever code executes.** A `native` profile is a developer convenience that must be chosen deliberately and shown as a warning in the UI. Application-layer allowlists are not a sandbox.
5. **Deny egress by default.** An automation reaches only the hosts its spec names, enforced at the sandbox boundary rather than in application code. This is the primary defence against a prompt-injected agent exfiltrating a repository.
6. **Repo content is untrusted input.** A README, issue or changelog can carry instructions aimed at the agent. Repo content may never widen a capability grant, and must be labelled as data in every prompt that carries it.
7. **Secrets never enter model context.** Injected into the sandbox as environment variables, redacted from logs, step traces, run artifacts and anything sent upstream.
8. **Push is not merge.** Draft pull requests by default. Auto-merge is opt-in per automation and conditional on gates passing.
9. **Every run is auditable.** Which model, which prompt, which commands, which files, what it cost, who approved it — retained, queryable and exportable.

Plus one operational requirement: **a kill switch** that stops every automation and revokes
every lease, reachable from desktop, web and CLI.

## 5. Capability configuration

Tool authority is configured in `~/.clerq/capabilities.json` and applied at gateway start
and on hot reload:

```json
{
  "fsRoot": "/absolute/path/you/choose",
  "fsMaxReadBytes": 1048576,
  "httpAllowlist": ["api.example.com"],
  "httpAllowedSchemes": ["https:"],
  "httpMaxBytes": 262144,
  "httpTimeoutMs": 10000,
  "httpAllowPrivateAddresses": false
}
```

| Key                         | Meaning                                                                                                                                | Default                         |
| --------------------------- | -------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------- |
| `fsRoot`                    | Root directory for `fs.read`                                                                                                           | the gateway's working directory |
| `fsMaxReadBytes`            | Largest file `fs.read` returns                                                                                                         | 1048576                         |
| `httpAllowlist`             | Hostnames `http.request` may reach. `*.example.com` matches subdomains but not the apex. Empty means the tool is not registered at all | _(empty)_                       |
| `httpAllowedSchemes`        | Permitted URL schemes                                                                                                                  | `["https:"]`                    |
| `httpMaxBytes`              | Response body retained before truncation                                                                                               | 262144                          |
| `httpTimeoutMs`             | Whole-request timeout                                                                                                                  | 10000                           |
| `httpAllowPrivateAddresses` | Permit loopback, private and link-local destinations                                                                                   | `false`                         |

Set the narrowest values that let your skills work. Do not point `fsRoot` at your home
directory, and turn on `httpAllowPrivateAddresses` only when you are deliberately targeting a
service on your own network — it disables the check that stops a redirected request reaching
your router or a cloud metadata endpoint.

## 6. Release checklist

Run before tagging any release.

### Secrets and keys

- [ ] No API keys in the frontend bundle, in logs, or in `config.json`
- [ ] Vault master key sourced from the OS keychain, not from the environment
- [ ] `GET /secrets` returns names only, never values
- [ ] The GitHub App's private key and client secret are in no route's answer, log line or run record (`github/gateway.integration.test.ts`, `automations/github-app.integration.test.ts`)
- [ ] The GitHub user token, refresh token and device code are in no route's answer, log line, audit row or run record (`github/signin.test.ts`, `github/signin.integration.test.ts`)
- [ ] Secret scan passes over the working tree and git history

### Gateway

- [ ] Binds `127.0.0.1` unless remote mode is explicitly configured
- [ ] All endpoints except `/health` and `/version` require a bearer token
- [ ] No `CLERQ_DEV` code path disables authentication
- [ ] CORS restricted to known origins; no `*`
- [ ] Rate limits and body size limits on webhook endpoints

### Tools and execution

- [ ] Path validation uses `realpath` + `path.relative`, with tests for traversal, symlink and prefix-sibling cases
- [ ] `http.request` validates every redirect hop and blocks private, loopback, link-local and metadata addresses
- [ ] Every executing tool runs inside a sandbox profile; `native` emits a visible warning
- [ ] Tool output is truncated before entering model context

### Desktop and updates

- [ ] Restrictive CSP set; `null` is not shipped
- [ ] Real updater public key configured; artifacts signed; a test update verifies end to end
- [ ] Installer disclaimer and About screen state actual permissions — see [INSTALLER_DISCLAIMER.md](INSTALLER_DISCLAIMER.md)

### CI

- [ ] Typecheck, Prettier check, Vitest, `cargo fmt`, `clippy` and `cargo test` all pass and are required
- [ ] `pnpm audit` and `cargo audit` clean or triaged with written justification
- [ ] Build succeeds on every target platform
