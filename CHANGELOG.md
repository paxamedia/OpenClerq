## [Unreleased]

### Added

- **Versioned API** ([docs/API.md](docs/API.md)). The protocol has one version, `API_VERSION = 1`, exported from `@clerq/gateway-client`. Every route is served under `/v1`; the bare paths keep working as aliases through 1.x. Every response, errors and the event stream included, carries `Clerq-Api-Version`, and a request may send it (none means 1). A version the gateway does not serve gets 400 `unsupported_api_version` before authentication, and a path and header that disagree get `api_version_mismatch`. `GET /version` (no token) reports the gateway's release, the API versions it serves and the newest applied schema; `GET /health` reports `api`. Within version 1 changes are additive only; clients must ignore fields and event types they do not know. `@clerq/gateway-client` calls `/v1`, sends the header on every request, turns a refused version into a `GatewayError` in plain words, and gains `checkCompatibility()` and `version()`; the desktop app checks once at start and shows a bar when the gateway cannot serve it. CORS allows and exposes `Clerq-Api-Version`.
- Contract tests: `api-surface.v1.json` files list the gateway's routes (read from the Express app) and the client's exported names. A removed or renamed one fails the test and says it needs API version 2; a new one fails until it is recorded with `CLERQ_UPDATE_API_SURFACE=1`.
- **Database backup before an upgrade** ([docs/UPGRADING.md](docs/UPGRADING.md)). When core migrations are pending on a database that already has some, a copy is written first (`VACUUM INTO`, tested on node:sqlite and bun:sqlite) to `~/.clerq/backups/clerq-schema<N>-<UTC time>.db`, mode 0600 in a 0700 folder; the newest five are kept. If the copy cannot be made, nothing is migrated and the gateway does not start. The log names the migrations that ran and the copy. One process upgrades at a time (a lock file, `clerq.db.upgrade-lock`): a second OpenClerq started on the same database waits, then carries on without a copy of its own. The copy is made private from its first byte (umask 077).
- A tripwire for the migrations: a test pins a SHA-256 of every shipped core migration, so editing one fails CI.
- Automation specs accept an optional top-level `version: 1`; any other version is refused at save, preview and parse with the line ("This automation was written for spec version 2; this OpenClerq reads version 1."). Parsed specs carry `version`.
- The desktop app writes the background service's output, and its exit code, to its own stderr as `[gateway]` lines, through a queue of 256 and a thread of their own, so a stderr nobody reads drops lines instead of stalling the service. They are the gateway's log lines, not redacted.
- **Automations.** A YAML spec (a subset of the format in `docs/ROADMAP.md` §4) runs a coding agent against a local repository, on a schedule or on demand: in a fresh git worktree started from origin's copy of the base branch, then the spec's gates, then a push and a draft pull request. New automations are saved disabled. Pushing waits in the approvals inbox unless the spec sets `approvals.push: auto`, and an automation's first push always waits. Endpoints under `/automations`, plus `GET /drivers` and `GET /runs/:id/artifacts/:id`.
- **`claude-code` driver** (`packages/drivers`). It runs Claude Code's CLI under the user's own sign-in, with no API key unless the spec names a vault secret.
- **`codex` and `cursor-agent` drivers.** `agent.driver` accepts both. `codex` runs `codex exec --json` in Codex's own sandbox (`workspace-write` for `acceptEdits`, with network access turned on because Codex turns it off there; `read-only` for the other modes); `cursor-agent` runs `cursor-agent --print --output-format stream-json`, which in agent mode edits the workspace and runs only commands on the user's own allowlist (`plan` and `default`/`dontAsk` use Cursor's plan and ask modes). `dontAsk` is the restrictive end in every driver, as in Claude Code. Both stream the same events as `claude-code`, stop their process group on cancel or timeout, and say plainly when the CLI is missing or not signed in; `detect` also reads the CLI's `--help` and names an option an older CLI lacks. Neither is ever started with its run-everything switch. Neither CLI reports a cost or takes a spend limit or a tool list, so a spec that sets `budget.max_usd_per_run`, `budget.max_usd_per_month` or `agent.allowed_tools` for them is refused when saved, naming the key. `agent.api_key_secret` is handed to the CLI as `CODEX_API_KEY` or `CURSOR_API_KEY`. Their output formats follow the vendors' documentation and are tested against fake CLIs only. Override the CLI path with `CLERQ_CODEX_BIN` or `CLERQ_CURSOR_BIN`.
- `GET /drivers` lists all three drivers, each with `signedIn` where the CLI says; a spec that does not name its own key needs the driver to be signed in.
- **Agent processes a crashed gateway left behind are stopped.** The gateway records every agent and gate process of a run (pid, process group, the OS's start time, command) in the new `run_processes` table, and on the next start stops what is still running before it marks interrupted runs failed and removes their worktrees, saying so on the run. A group is stopped only if its leader is still there with the recorded start time and, for an agent, a command line that still names the CLI; the leader is read again just before the group is signalled, and a group whose leader has gone, or a record with no start time, is left alone. Runs now carry the pid and start time of the gateway that created them, and a run whose gateway is still running is not treated as interrupted. Needs `ps` with `lstart` (macOS, procps).
- When an agent or a gate exits, anything it left running in its process group is stopped. `exec()` in `@clerq/sandbox` gains `onSpawn` and `reapGroup` options.
- Budgets per run (passed to the CLI) and per month (pausing the automation), one run per automation at a time, and a global cap, `CLERQ_MAX_CONCURRENT_RUNS`; runs beyond it wait in the queue.
- A run records the worktree, the agent's tool calls, each gate, the commit, the push and the PR as steps, and keeps the diff and the agent's output. A run interrupted by a restart has its worktree removed and is marked failed, or retried when its spec allows.
- Desktop **Automations** module: a spec editor that checks a spec against this machine before saving, runs with their steps and diff, and the approvals inbox.
- `packages/web`, the start of the rebuilt desktop interface: design tokens for light and dark, bundled DM Sans and JetBrains Mono, an icon wrapper, and tests that fail on corners over 1px, inline styles, colours or fonts outside the tokens, and text contrast below WCAG AA.
- `GET /events/stream`: the event bus as resumable SSE, with `Last-Event-ID`, a `reset` frame, name filters and a heartbeat. `gateway.streamEvents()` and `gateway.eventsStreamUrl()` in `@clerq/gateway-client`.
- **Module platform.** A module's `register(ctx)` gets a ModuleContext: routes, store, secrets, approvals, audit, logger and config, scoped to its id. Types in the new `@clerq/module-sdk`, with a hello-world example. `GET /modules` lists modules and whether each loaded.
- Module migrations: `<module>/migrations/NNNN_name.sql`, applied by `packages/store` and limited to tables named `mod_<id>__*`.
- Module events: `ctx.events.emit('x')` puts `module.<id>.x` on the event bus.
- Module handler triggers (cron, file, webhook), each firing recorded as a run with `moduleId` and `triggerId`, and paused by the kill switch.
- Scoped module tokens: `POST /modules/:id/token` issues a short-lived token valid for `/api/modules/:id/*` plus the manifest's `coreEndpoints`; `DELETE /modules/:id/tokens` revokes them.
- Module UIs: the gateway serves `<module>/dist/ui` at `/api/modules/:id/ui/`.
- `ctx.notify` and `ctx.notify.badge` emit `notify.posted` and `notify.badge` for the desktop and devices. `@clerq/gateway-client` gains `modules()`, `moduleToken()`, `revokeModuleTokens()` and `fireModuleTrigger()`.
- Module services: start, stop and status for the launchd agents a manifest declares, as `ctx.services` and under `/api/modules/:id/services`.
- **Shared records**: people, organisations and activities with identity resolution by email, phone and domain, refs (`<module>:<type>:<id>`), links between any refs, and merge. Endpoints under `/records`, `/links` and `/activities`; `ctx.records` for modules.
- Manifest `extensions` (`nav`, `home.tile`, `record.panel`, `record.action`, `search`, `inbox.item`, `settings.page`) listed at `GET /extensions`; `GET /search` across core records and modules; one inbox at `GET /inbox` with module items and pending approvals.
- **Tenants**: records, links, activities, inbox items and every module table carry a `tenant_id` (default `default`). A request's tenant comes from its scoped token or `X-Clerq-Tenant`; `ctx.tenant`, `ctx.withTenant()` and the tenant-scoped `ctx.store.rows()` for modules. A single-tenant install behaves as before.
- **Remote mode and device pairing**: an opt-in HTTPS address for the user's tunnel, single-use pairing codes valid five minutes, device tokens scoped to the mobile API set with last-seen and instant revocation. The gateway stays on loopback.
- Push to paired phones through ntfy, one random topic per device: approvals, new inbox items, failed runs and module notifications, as a generic title and an id only.
- Manifest `permissions` are parsed, listed at `GET /modules`, stored, and audited when they change. Not enforced.
- Automation summaries carry `monthBudgetUsd` and `nextFirings` (the next ten); `GET /runs` takes `since`.
- Component kit in `packages/web` for the new interface: buttons, fields, checkbox, switch, segmented control, tabs, a sortable table, run status tags, key–value lists, code blocks, skeletons, empty states, tooltips, popovers, menus, dialogs, a drawer and toasts. All keyboard-operable; the Foundations page shows each one in both themes.
- **New interface** in `packages/web`, mounted by the desktop: a rail (bottom tabs at phone width), a top bar, a status bar with connection, running runs and month spend, a ⌘K palette that searches records and every module, and routes for every page (`#/runs/<id>`, `#/m/<module>/<path>`) with Back across modules. Pages follow `/events/stream` live.
- Home with tiles and 14-day sparklines, an activity timeline, next runs, what needs you, a first-run checklist and module tiles. Automations with run strips, budget meters, a schedule heatmap, cost per run and an editor that checks the spec as you type. Runs with filters, a pipeline stepper, a step waterfall and a diff viewer. One inbox for approvals and module items, with J/K/A/D keys. Records with module panels and actions. Chat with an inspector and comparison bars.
- Settings in the main window: General (theme, start page, emergency stop), Models & keys with a **Test** per provider, Secrets, Skills, Memory, Triggers, Remote, Devices (pairing QR, last seen, revoke), Advanced, and modules' own settings pages. Developer: tool runner, calculator, task runner with context preview, live log, service figures.
- Module UIs in a frame with a token bridge; module notifications as native notifications; the inbox count on the app icon; a content security policy that allows only the loopback gateway.
- `pnpm ui:shots`: every page in both themes at three sizes, over fixture data.
- **Tool calling in `@clerq/providers`.** `call` and `callStream` take `tools` and a conversation of text, tool-call and tool-result blocks, and return the model's `toolCalls`, its whole turn as `content` and a normalised `stopReason`, for the `anthropic` adapter (`tool_use` / `tool_result`, streamed `input_json_delta`) and `openai-compat` (`tools` / `tool_calls` / `role: "tool"`, streamed argument fragments). Tool input that is not valid JSON is flagged rather than guessed at. Anthropic `thinking` blocks are handed back unchanged; an OpenAI-compatible server's `reasoning_content` is sent back only when its registry entry sets `replayReasoning: true`. Tokens and cost are recorded per call as before; an unpriced cloud model's cost stays unknown.
- **Context management** in `@clerq/providers`: token estimation (the provider's count once reported, a documented heuristic until then), a context budget from the registry's context window, a conversation with pinned turns and rolling history, compaction that has the model summarise older turns (or drops them with a note, keeping any earlier summary), skipped when it would free too little, and tool-output truncation that says how to get the rest.
- **`builtin` agent driver.** `agent.driver: builtin` with `agent.model: <provider>/<model>` runs OpenClerq's own tool loop over any model in the registry. Its tools read, list, search, write and edit files in the run's worktree, run shell commands through the sandbox, and show `git status` and `git diff`. Every call goes through `packages/policy`: full access by default, a push from the shell waits for approval in every mode, `permission_mode: default` sends writes and commands to the approvals inbox, and `agent.allowed_tools` takes policy rules. Paths follow links whose target does not exist yet, and writes do not follow a link. Tool inputs and outputs are redacted of the vault values the run uses. An approval the agent is waiting on is closed when the agent stops or runs out of time. Bounded by 60 turns, `sandbox.timeout`, 400 tool calls and `budget.max_usd_per_run`, measured from recorded cost with each next call counted at its full output limit; a dollar budget for an unpriced cloud model fails the spec check. A turn cut off at the output limit does not run its last tool call, and a turn that ends without an answer fails the run. Each model call is a run step with its tokens and cost, and older context is compacted when the window fills. `GET /drivers` lists it with each provider's readiness. Tested against a scripted model only.
- Every tool call an agent makes is also a row in the new `tool_calls` table (store migration 13), with whether a person was asked.
- **Durable run queue with leases.** Automation runs are queued as rows (`queued`), leased by a gateway (`leased`, `lease_until`, renewed while the run works) and survive a restart. A run whose lease has expired and whose gateway is gone is claimed in one conditional write, so two gateways on one store cannot both settle it, then its processes are stopped, its worktree removed, and it is retried or failed; a run only leased is put back at most three times. A queued run can be cancelled, switching an automation off cancels its queued runs, and the kill switch cancels queued runs and holds the queue. The kill switch's pause is kept in the store, so a restart does not release it. The desktop says when a started run has to wait. `POST /automations/:id/run` answers `queued: true` when the run waits for a place. Store migration 14 (`runs.attempt`, `runs.not_before`, `automations.last_slot_at`).
- **Missed-schedule catch-up.** A slot missed while the machine slept or the gateway was down runs once when noticed with `on.catch_up: true`, however many were missed; without it the slots are skipped and recorded (audit log `automation.slots_missed`, event `schedule.missed`, `missedSlots` in the automation summary), and so is a slot whose run could not be queued. A slot is claimed by compare-and-set in the same transaction as its run, so two gateways on one store cannot both fire it. Sleep is noticed as the wall clock jumping past the monotonic clock (`schedule.woke`). Slots missed while the kill switch held schedules are never caught up.
- **Fair scheduling across repositories.** With more runs queued than `CLERQ_MAX_CONCURRENT_RUNS` allows, the next is taken from the repository with the fewest runs going, then the one served longest ago, oldest first within it. `targets.max_parallel` stays refused: targets are one repository per automation.
- **Retries with backoff.** `retry.max_retries` and `retry.backoff` (doubling, at most an hour) retry a run after an agent crash, a provider 5xx/429 or outage, or an expired lease, never after a policy decision, a budget, a time limit, a denial, a gate or a cancel, nor once the automation is switched off. Only what the driver reports is read, never the agent's final message. Every attempt is one run, under one `max_usd_per_run` for what the attempts reported; a crashed attempt with no reported cost makes the run's cost a lower bound. Drivers report `crashed` when the CLI exited without a result, and `apiError` for an API error the CLI itself printed.
- **Model escalation on gate failure.** `agent.model.escalate: [model, …]` runs the agent again with the next model when a gate fails, in the same worktree, with the failed check in its prompt; one commit per run. Each attempt is an `agent.escalate` step and gets only what is left of the run budget; the month budget is checked before each. Every model is checked before the run starts, so an unpriced model with a dollar budget is refused at the spec check (builtin). Event `model.escalated`.
- **Gate diff assertions.** `assert: diff.files_changed | diff.lines_added | diff.lines_removed <op> N` and `assert: diff.touches_none_of | diff.touches_only [globs]`, read by a small parser when the spec is saved (errors carry line and column), checked against the run's diff from its base, each recorded as a gate step.
- **Model fallback.** `agent.model.fallback: [model, …]` names the models to use, in order, when the one in use is unavailable: its provider is down, overloaded or rate limiting, did not answer, refused the key, or has no key. It is decided from what the provider adapter reports about the failed call (`ProviderError.unavailable` in `@clerq/providers`), never from the words of an answer; a request the provider refused as malformed, or an unknown model id, never falls back. The builtin agent switches in the middle of its run (the failed call is recorded, the old model's reasoning is dropped from the history, the conversation is fitted to the new model's window, and the turn does not count against the turn limit); a CLI agent is started again with the next model at once, without a backoff or a retry used, and told what the interrupted attempt left in the worktree. When every model is unavailable the run fails, and `retry` may take it from the top. Each move is a `model.fallback` event with the run (and chat session), a `model.fallback` run step, and `llm_fallbacks_total` in `GET /metrics`. Budgets keep applying: each attempt is held to what is left, and a fallback model with no price under a dollar budget is refused at the spec check. The run starts on a fallback only when the primary's provider has no key or a local server is not running (`DriverAvailability.reasonKind`); a provider the registry does not know, an unpriced primary or a CLI that is missing is an error, and a spec saved or previewed with a builtin model on an unknown provider is refused with its line. `agent.model.strategy` stays refused, now saying it is planned after 1.0 and which keys to use instead.
- **Strictness.** A model a person chose is used as chosen. `POST /automations/:id/run` takes `{ "model": "…" }`, which runs that model in place of the spec's primary and never falls back (the choice is kept through a retry; store migration 15, `runs.model_override`). The spec's models, and the defaults, may.
- **A default chain for chat and tasks.** `PUT /routing { fallback: ["provider/model", …] }` (read with `GET /routing`) names the models managed chat, `/task`, `/explain` and gateway triggers use when the default model is unavailable. A call that names a model (`/task` or `/explain` `model`, a session's model, a comparison column) uses it as chosen, and so does every raw-mode message, since a raw call is one request to one model. A stream that has already sent text is never moved. Empty by default.
- The builtin agent's API key (`agent.api_key_secret`) is only given to models of the provider of the spec's own primary model, so a fallback, an escalation or a model named for one run on another provider uses that provider's own key and the key is never sent to a vendor it was not for. A spec check and a run check every model of the chain through one function.
- **Memory 2.0.** Memory records have a type (`fact`, `preference`, `decision`, `procedure`, `note`), any number to a key, an origin, a confidence, a source session and an expiry. Search is SQLite FTS5, best match first (the key counts more than the value), falling back to substring match where the SQLite in use has no FTS5 or nothing matches by word; checked under Node and Bun. A model can fold the records of one key into one (`POST /memory/consolidate`, a run of its own, an audit entry, the records kept as `superseded`), and `POST /memory/records/:id/unconsolidate` restores them. The summary expires with the latest of its sources (never, if any source does not), carries `agentDerived` when any source came from an agent (store migration 17), and deleting or expiring a summary removes everything folded into it, at any depth; undoing a summary that is itself folded into another is refused. Managed chats and `/task` read memory into the system prompt under a policy of `memory.read.<type>` rules in `packages/policy`: the preferences always, other types by relevance, only the types the policy allows (`GET`/`PUT /memory/policy`, every type by default). An automation reads memory only when its spec says so (`memory: { read: [types] }`, off by default, so an unattended run does not send saved notes to a model unasked): the types become `memory.read.<type>` rules of the run's own policy, and what was read is a run step. Raw mode reads nothing, and neither do cron, file and webhook triggers. Every `<` and `>` in a note's key or value is escaped in the block. Expired records are never read, and are removed at start and when memory is read, at most hourly. `memory.updated` is emitted for every change. New endpoints under `/memory/records`, `/memory/search`, `/memory/consolidate` and `/memory/policy`; the Memory screen in Settings picks a type and searches. Store migration 16 rebuilds the `memory` table and copies every existing row across with its dates, keeping its type when it is one of the five (anything else becomes `fact`) and marking its origin `import`; migration 17 adds `agent_derived`. `memory.write.<type>` and `writableMemoryTypes` in `packages/policy` are reserved for an agent's memory tool: only reading is enforced.
- **Sub-agents for the builtin agent.** Off by default: a builtin spec turns them on with `agent.subagents: { enabled: true, max_concurrent?: 1-4, models?: [provider/model] }`, or by naming `sessions.spawn` in `agent.allowed_tools` (`*`, `risk:write` and `group:sessions` do not). In such a run, the builtin agent can call `sessions.spawn` (`spawn_agent`) to start a sub-agent with a task, optionally a narrower tool set and a model, and gets back its final answer and a short trace. Each sub-agent is a run of its own (trigger `subagent`, `parentRunId`) with a session for its transcript, recorded with steps, tool calls and cost, listed in `GET /runs`; a run's detail lists its `children` and `childCostUsd`, and the run view links both ways. Its policy is the parent's cut down to what it asks for, read-only by default, never wider (`narrowRules` in `packages/policy`), and never includes `sessions.spawn` (one level deep, enforced in code). It reads at most the memory types the parent reads. At most four run at once per parent (or `max_concurrent`); one more waits. They share the parent's worktree and what is left of its run budget (checked before every model call, with calls in flight held), count toward the automation's month, stop when the parent is cancelled or times out, and ask for approval in the same inbox naming the parent run (`parentRunId` on approvals and on run events). A model named for a sub-agent must be in the spec's chain, the run's chosen model or `agent.subagents.models`, and is used as named; otherwise it inherits the parent's model and fallbacks. With only a monthly budget, the shared pool is what is left of the month. The parent shows `awaiting_approval` until no approval of it or its sub-agents is open. Store migration 18 adds `runs.parent_run_id`. The CLI drivers' own sub-agent features are not covered.

- **Seatbelt and container profiles for automation runs, opt-in.** `sandbox.profile: seatbelt | container` runs the agent, the builtin agent's commands and the gates inside the profile; `native` stays the default, `sandbox` may be left out (the run records that it is unisolated), and the native profile refuses `sandbox.network` and `sandbox.filesystem` with the reason. Under both profiles writes are limited to the run's worktree (`filesystem: repo_only`) and the worktree's own index, the repository's git directory is read-only (config, hooks, refs and objects; the agent can stage but not commit, and the gateway commits its changes), and the `.git` pointer files cannot be changed. Seatbelt reads the disk except known credential stores and OpenClerq's own state, runs an agent CLI on a state home of the run's own (it needs `agent.api_key_secret` under either profile, and your own `~/.claude`, `~/.codex` and `~/.cursor` stay unreadable), runs the builtin agent's file tools inside the profile, keeps writable directories and the directories above them from being moved or replaced, refuses Unix-domain sockets (also under `network: all`) and allows only named mach services (not LaunchServices); a container sees only the worktree and the git directory, at the same paths, and needs `sandbox.image` and, for a CLI, `agent.api_key_secret`. Egress is limited to `sandbox.network` plus the hosts the agent CLI's provider needs, through an egress proxy (`all` lifts the limit): on macOS a local proxy with the network denied but its port, in a container a proxy container on an internal network. Codex is started with `--sandbox danger-full-access` under an outer profile (its own sandbox cannot nest inside seatbelt) and a read-only mode makes the worktree read-only. Containers are named per run and removed by name on exit, timeout, cancel and at the next start after a crash (store migration 19, `run_processes.container`). The container profile is tested against a fake runtime only.
- **Remote repositories.** `targets.repos` takes `github:owner/name`, `gitlab:group/name` or an https URL on github.com or gitlab.com (`#branch` for a base other than the default). The repository is cloned once into the workspace cache, fetched before each run, and each run gets a worktree from origin's base branch; the branch is pushed and a draft pull request (GitLab: merge request) opened through the existing publish path. The token is `publish.token_secret` (default `GITHUB_TOKEN`, or `GITLAB_TOKEN` for GitLab), sent to git only as an HTTP header for the forge's host in the environment of the git command, never stored in the clone; lookups go through one credential function (`forgeCredentials`) so another source can replace the vault. A local repository whose origin is on GitLab can now open a merge request too (name its token in `publish.token_secret`). One repository per automation, as before.
- The diff stored with a run is redacted of the vault values the run uses (its model key and forge token), and so are gate output, the commit message and the pull request's title and body. Matching is literal, for values of 6 characters or more. The diff is also scanned with every file read as text, so a file marked `-diff` or holding a NUL byte is scanned too. A secret the agent writes into a file is still in the commit: when the diff contains one, the run says so and the push waits for approval whatever `approvals.push` says.
- The run's commit is made with plumbing from an index of the gateway's own: the base as its only parent, merge state in the worktree removed and ignored, and the branch checked to be the base plus that commit before it is pushed by its id. After the agent and the gates, processes the run left behind (found by a tag file every command holds, or by `lsof` under the run's directories and started since the run began) are killed, or the run fails; processes that predate the run are reported and left running. Under a profile the gates run on a fresh checkout of the run's commit, and worktrees are moved aside before they are deleted; `exec()` awaits its process-group reap.
- After an agent or a gate has run, the gateway checks that the worktree and its git entry are the directories they were, and fails the run without running git in them if not. Its git commands there run without fsmonitor, hooks, submodule recursion, external diff or textconv, and a nested repository staged by the agent is refused before the commit. The builtin agent's file tools pin the worktree for the run.
- `@clerq/sandbox`: seatbelt gains `denyRead`, `readOnly`, `protect`, `allowWritePrefix` and `readOnlyCwd`; the container profile mounts paths at their host paths, runs as the host user with `--init`, names its container (`onSpawn` reports it), removes it when the command ends, and enforces an egress allowlist with a proxy container (`removeContainer`, `CLERQ_CONTAINER_RUNTIME`, `CLERQ_EGRESS_IMAGE`). `@clerq/workspaces`: `parseRemote`, `forgeOf`, `forgeAuthEnv`, `Workspace.gitDirs()`, and remote clones made without a checkout, under a temporary name, one at a time.
- **Chat console managed mode.** A managed message now runs the builtin agent loop as its run: the system prompt, the selected skill and the memory block, earlier turns as rolling history with compaction, and a tool set decided by `packages/policy`: search saved notes (the types the memory policy allows), save a note (`memory.write.<type>`, marked as the agent's, with the conversation; a preference or procedure always waits for approval, any note in `default`), draft an automation, and the builtin repository tools only in a folder attached to the conversation (`POST /sessions/:id/update { workspace, permissionMode }`: full access by default, `default` asks before writes and commands, `plan` reads only, `sandboxed` on macOS runs commands and file tools under seatbelt with writes only in the folder, no network and credential stores unreadable; `git push` and `gh pr create` are recognised by word and wait, which a command that hides the word gets past). Without a folder there are no file, shell or git tools. A folder that is, holds or lies inside `~/.clerq` or the store's directory cannot be attached. Commands get `HOME` set to a directory of the conversation's own, with the commit name and email passed in, so tools that find your files through `$HOME` (git's global config and a credential helper set there, shell dotfiles) do not see them. This is not isolation: ssh takes your home from your account, not `$HOME`, so a push over ssh still uses `~/.ssh` and its keys, and a credential helper in the system git config (macOS's keychain helper) still answers. Under Full access the agent's commands run as you and can do anything your account can, including read the gateway token by its full path and drive the gateway; the folder dialog says so. A call that needs approval waits in the inbox and appears in the chat with **Approve** and **Deny**; provider keys and the gateway token are redacted from tool input and output; steps, tool calls and model calls are recorded on the message's run, which carries the session. Raw mode is unchanged: no prompt, memory or tools, whatever the session holds. `POST /sessions/:id/mode-diff` returns what managed adds for a message (system prompt, skill, memory, tools with their policy decision, model and fallback chain), and the chat inspector shows it as additions. Tested against a scripted model only.
- **Conversational automation authoring.** In a managed chat the model can draft an automation with `draft_automation`; the spec parser checks it and an error goes back to the model with its line. The chat shows a card with **Preview YAML**, **Dry run** (the preview's checks, the next runs as real dates in the host's time zone, a cost estimate from past runs of the same driver and model when there are any; nothing executed) and **Save**. Save is allowed once that YAML has been dry-run (store migration 21). A saved draft is an automation that starts switched off and records `authored_by: chat <session>`, shown as "Written by a chat" beside its switch; the card shows the prompt, gates, isolation, permission mode, tools, memory read and warnings (push without asking, no isolation, gate commands); its first push waits for approval whatever the draft asked. No chat tool can save, enable, edit or run an automation, and every chat's policy denies those actions by name (a Full access command is not a tool and is not stopped by this). Endpoints `GET /sessions/:id/drafts[/:draftId]`, `POST /sessions/:id/drafts/:draftId/dry-run|save`; store migration 20 (`automation_drafts`, `automations.authored_by`).
- `GET /runs/:id` lists the run's `toolCalls`, also at `GET /runs/:id/tool-calls`; `GET /approvals` gives a chat's `sessionId`. `@clerq/gateway-client` gains `modeDiff`, `drafts`, `draft`, `dryRunDraft`, `saveDraft`, `runToolCalls` and an `onEvent` handler on `sendMessage`.
- `memory.include_agent: true` in a spec lets an automation read notes an agent wrote; without it they are left out, and in a managed chat's prompt they are labelled.
- The builtin driver takes earlier turns (`history`), runs without repository tools (`repositoryTools: false`), and offers a caller's own tools (`extraTools`) under the same policy.
- **Repos.** `GET /repos` and `GET /repos/:id` (behind the token like every route, read-only) list the repositories automations have targeted: kind, `owner/name` or folder name, URL, where it is on this computer and whether it still is (a folder that has gone is listed, not hidden), the automations that target it, each with the vault secret its own spec reaches the forge with (`publish.token_secret` or the forge's default name; the name and whether the vault holds it, never the value; a local repository only when the automation pushes or opens a pull request), runs queued and running, the last run, and in the detail its latest 20 runs. A repository appears once an automation naming it in `targets.repos` has been queued. A request reads `runs` once for all repositories and asks the vault for its names, never opening a secret. The **Repos** page in the interface lists and opens them and links to automations and runs. `@clerq/gateway-client` gains `repos()` and `repo(id)`.
- `GET /runs` carries `childCostUsd` for a run that started sub-agents, as `GET /runs/:id` already did, and both carry `childCostKnown: false` when a sub-agent made a model call with no price, so that figure is a lower bound.
- **Run page.** The tool calls an agent made (tool, whether it was allowed or a person approved it, a short input, how long it took; input and output on demand, long output folded). Steps for a model fallback, a model chosen for the run, an escalation, a sub-agent start, the sandbox profile (native shown as a warning), a vault secret in the diff, a clone, hosts a gate could not reach, a retry, a requeue, a caught-up schedule, saved notes read and a compacted context read in words, with a note in the step's detail. Sub-agents are a tree under the run that started them, each with its status and cost; the Runs list and the run's facts add what they cost to the run's own, as "at least" when a sub-agent's call had no price.
- Approvals in the inbox name the run a sub-agent belongs to and link the chat that is waiting for the answer. The automations list shows a waiting run, whether a schedule catches up, missed times and why, and a spec a chat drafted; **Run with a chosen model** (More actions) runs it with a model you name, used as named with no fallback.
- Settings: **Fallback models** (Models & keys) edits the default chain behind `GET` and `PUT /routing` and says a fallback sends the prompt to another provider; **Memory** edits what chats and tasks may read (`/memory/policy`), shows who wrote each record, summarises records with a model and undoes a summary, and can list the records folded into a summary.
- **`clerq-server`**, the gateway as a headless daemon (`apps/server`, [docs/SERVER.md](docs/SERVER.md)). It reads only the environment and `~/.clerq/.env` (never the working directory's `.env`), logs its address, data directory, where the token is (never the token), the versions and a warning when bound beyond loopback, and on SIGTERM or SIGINT stops accepting connections, stops the schedules and the queue, closes the store and exits 0 (1 if that takes over 10 s). A run in flight is left for the next start's recovery. `clerq-server healthcheck` asks `/v1/health` and exits 0 or 1 (no `curl` needed), `version [--json]` prints the release, API version and store schema, and a `clerq-calc` next to the executable is used when `CLERQ_CALC_PATH` is not set. Example systemd units for a system service (own account, `StateDirectory`, hardening) and a user service are in `apps/server/systemd/`; the docs cover settings, data and backups, upgrading, security notes, and reverse-proxy examples for Caddy and nginx (event streams, body size, the token).
- `scripts/build-binary.js` compiles an entry point with Bun for one `--target` (linux x64/arm64, macOS, Windows, musl) into `<package>/dist/<target>/`, with `clerq-calc` beside it when one is built for that target, and without Bun's automatic `.env` loading. `apps/server/scripts/smoke.mjs` runs a built binary: public and protected routes, the token, healthcheck, SIGTERM. CI builds and smoke-tests the linux-x64 server and runs `systemd-analyze verify` on both units.
- `createGateway()` returns `close()`: stop listening, stop the schedules, queue, triggers and push publisher, close the store.

### Removed

- The 0.5 interface: the entry screen, mode picker, Builder/Operator toggle and the separate settings window. Their features are in the new pages.

### Changed

- A database written by a newer OpenClerq is refused instead of opened: the gateway logs "This database was written by a newer OpenClerq (schema 23); this build knows schema 21. Install the newer version, or restore a backup from ~/.clerq/backups.", stops serving and exits with code 1 (`createGateway().ready` rejects). A module that ships fewer migrations than its data has applied is refused the same way, and listed as failed at `GET /modules`.
- `@clerq/gateway-client` addresses every route under `/v1` and sends `Clerq-Api-Version`; `eventsStreamUrl()` and `logsStreamUrl()` return `/v1/...` addresses. `@clerq/gateway` depends on `@clerq/gateway-client` for the version constant.
- The module manifest schema accepts `config`, `coreEndpoints`, `services`, `permissions` and `extensions`.
- `packages/sandbox` gives a command a minimal environment unless `inheritEnv` is set, streams output line by line, and stops on an abort signal.
- Automations run without isolation unless their spec opts into a profile; `sandbox` may be left out (it means `native`).
- An OpenAI-compatible server that refuses `max_tokens` and names `max_completion_tokens` instead (OpenAI's reasoning models) is retried once with it.
- A managed chat message no longer runs the `/task` pipeline (and its calculation step); it runs the agent described above. `/task`, `/explain` and triggers are unchanged.
- The canonical path-containment check moved from the gateway to `@clerq/sandbox` (`resolveWithinRoot`), so the agent drivers use the same one.
- `GET /memory`, `GET /memory/:key` and `POST /memory` answer as before with the record's `id`, `type`, `origin`, `status` and other fields added; a key may now appear more than once, and `DELETE /memory/:key` forgets all of them. A key set with `POST /memory` is still one `fact`, updated in place. Two compatibility changes: `GET /memory` lists at most 500 records (`?limit=`, up to 1,000; it listed every entry), and `POST /memory` answers 400 for a value over 20,000 characters (it stored any size).
- Closing the store folds its write-ahead log into `clerq.db`, so after a clean stop the file alone is the whole database (a copy of just `clerq.db`, as [UPGRADING.md](docs/UPGRADING.md) describes, misses nothing). Under Bun the log was left beside the file.

### Fixed

- Deleting a memory entry from the desktop sent no gateway token.
- Cron triggers with a weekday or day-of-month field, such as `0 8 * * 1`, could fail to fire: node-cron 4.2.1 miscalculated when they were next due. Upgraded to 4.6.0.
- A module list saved in the desktop settings hid modules bundled with later releases.
- A gateway whose port could not be bound (in use, or not permitted) went on as if it were serving; `ready` now rejects with the reason, and `clerq-server` exits 1 with it.
- Finding the processes a sandboxed command left behind compared their start time from `ps -o lstart` with the run's start. On Linux `lstart` is boot time plus ticks and follows the wall clock, so after an NTP step a process the run started could look older than the run and be left running. It now compares elapsed time (`etime`), which does not drift.

### Security

- `body-parser` and `qs`, used by Express in the gateway, are pinned to their patched releases.
- The desktop's `rustls-webpki` and `webpki-root-certs` are updated past advisories that let distrusted certificate intermediates verify.
- Build and test tooling moves to `vite` 7.3.7 and `vitest` 5.0.5, past advisories in the dev server and the test mocker.

## [0.4.0] — Security foundation

**Breaking:** the gateway API now requires authentication.

### Security

- **Gateway authentication.** Every endpoint except `GET /health` requires `Authorization: Bearer <token>`, compared in constant time. The token is generated at `~/.clerq/gateway-token` (mode 0600) on first run, or supplied with `CLERQ_GATEWAY_TOKEN`. `CLERQ_DEV` no longer affects access.
- **Licensing no longer stands in for authentication.** The license middleware attaches entitlement information and never rejects.
- **Loopback binding.** The gateway binds `127.0.0.1` unless `CLERQ_HOST` is set, which logs a warning. It previously bound all interfaces.
- **Path containment.** `fs.read` resolves against the real path of its root and rejects traversal, sibling-prefix escapes, absolute and UNC paths, NUL bytes, escaping symlinks, non-regular files and reads over `fsMaxReadBytes`.
- **SSRF hardening.** `http.request` allows https only by default, refuses credentials in URLs, blocks loopback, private, CGNAT, link-local, multicast and cloud-metadata addresses (including IPv4-mapped forms), checks every redirect, and bounds redirects, time and response size.
- **CORS** reflects only allow-listed origins.
- **Request bodies** are capped at 1 MiB (`CLERQ_MAX_BODY`).

### Added

- `capabilities.json` options: `fsMaxReadBytes`, `httpAllowedSchemes`, `httpMaxBytes`, `httpTimeoutMs`, `httpAllowPrivateAddresses`.
- `setGatewayToken()` and `hasGatewayToken()` in `@clerq/gateway-client`; the desktop app loads the token before its first request.
- **Control Tower** with Builder and Operator modes.
- **Skill schema editing** — input and output JSON schemas and dependencies; `GET`/`PUT /skills/:slug`.
- **Context preview** — what would be sent to the model, without calling it (`POST /context/preview`).
- **Dry runs** — `dryRun: true` on `/task` shows the trace without calling a model or the calculation engine.
- **Step traces** with durations in `/task` responses.
- **Memory** — list, add and delete through `/memory` and the desktop app.
- **Metrics** — `/metrics` reports model calls, latency, tokens and failure rate.
- **Capabilities, reasoning and system prompt settings** — `GET`/`POST /capabilities`, `/reasoning`, `/system-prompt`.
- A standalone Settings window, keyboard shortcuts, and a retry button when models fail to load.
- macOS signing and notarization support, and the Tauri updater (see `docs/DISTRIBUTION.md`).
- CI: type checks, tests, Rust checks, dependency audits and a secret scan; macOS and Windows installer builds; tag-triggered releases.

### Changed

- One version across every package, the Tauri config and the version `/health` reports (`node scripts/sync-version.js [version]`).
- The documented `curl` examples send the bearer token.
- Settings moved from a modal to its own window.

### Fixed

- Dependency vulnerabilities (14 high, 1 critical). Unused `ws` and `zod` were removed, and `path-to-regexp` is pinned to a patched version.
- `SKILL.md` frontmatter in single quotes (`slug: 'my-skill'`) is parsed; the quotes used to become part of the value.

### Removed

- The `fsAllowWrite` capability flag, which no tool ever read.

### Documentation

- `ROADMAP.md`, `SECURITY.md` (threat model, rules, known gaps, release checklist), and corrections to `ARCHITECTURE.md` and `TOOLS.md`. `SAFETY_CHECKLIST.md` and `ERROR_RESPONSE_SHAPE.md` were folded into them.
